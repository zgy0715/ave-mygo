# 18 · 工程深度与体量方案（毕业设计级）

> **定位**：`docs/17-后续演进计划.md` 回答"做什么功能"；本文回答"**要做多深、怎么证明它够深**"。
> 不做论文、不做实验设计——要的是**毕业设计那样的工程体量与技术难度**。
>
> **核实基准**：2026-11-02 18:50。**所有规模数字以 [docs/metrics.md](metrics.md) 为准**（本文不重复维护，
> 否则一轮功能改动就会让"实测"变成"过期"）。当前迁移已到 **V55**，新迁移从 **V56** 起。

---

## 0. 结论先行：你缺的不是体量，是"硬核模块"

先把你担心的"体量够不够"量化掉（实测）：

| 维度 | **当前实测** | 本科毕设常见量级 | 判定 |
|---|---|---|---|
| 后端代码 | 119 个 Java 文件 / **8252 行** | 8k ~ 15k 行 | ✅ 已达下限 |
| 前端代码 | 75 个文件（43 个 `.vue`）/ **9236 行** | 6k ~ 12k 行 | ✅ 已达标 |
| 后端测试 | **149 例 / 31 个测试类** | 视学校要求 | ✅ 有 |
| 数据表 | **18 张业务表**（+ flyway 历史表） | 15 ~ 25 张 | ✅ 达标 |
| 接口 | **61 个** | 40 ~ 70 个 | ✅ 达标 |
| 页面 | **14 个业务路由** | 15 ~ 25 个 | 🟡 略少 |
| **技术难点** | **2 ~ 3 个**（票务并发、Agent 工具编排） | 需要 **6 ~ 8 个** | ❌ **主要差距** |
| **非功能能力** | 限流 / CORS / 审计 / 备份（零散） | 权限、缓存、报表、媒体、实时、可观测 | ❌ **主要差距** |
| **可量化成果** | 无压测、无性能报告 | 有数据支撑 | ❌ **主要差距** |

**结论**：16.4k 行代码、18 张业务表、61 个接口——**体量已经够毕设了**。你觉得"不够深"，是因为**功能集中在 CRUD 层**，缺的是"能被追问三层"的模块，以及"能用数字说话"的证明。

所以下面的方案不是"加更多功能"，而是**加 7 个有技术门槛的模块 + 3 项非功能底座 + 1 套可量化证明**。

## 1. 先定义"什么算深"

### 1.1 深度三级（判断标准）

| 等级 | 特征 | 例子 | 能否被追问三层 |
|---|---|---|---|
| **L1 CRUD** | 增删改查 + 分页 + 前端表格 | 歌曲管理、用户管理、评论 | ❌ 追问"并发怎么办"就露底 |
| **L2 业务** | 状态机、配额、校验规则、多表事务 | 票务下单（CAS 抢状态 + 配额回滚）、歌单录入 | 🟡 能答一层 |
| **L3 技术** | 并发控制、一致性、性能优化、架构取舍、可观测 | 库存扣减压测、延迟队列、RBAC 数据权限、媒体处理流水线、检索排序 | ✅ 能答三层 |

**毕业设计的"难度"= L3 模块的数量 + 每个模块能讲清"为什么这么做、比另一种做法好在哪、拿什么数据证明"。**

### 1.2 现有模块深度盘点（实测）

| 模块 | 当前实现（代码事实） | 深度 | 加厚空间 |
|---|---|---|---|
| 认证 | JWT + `user.role` 单字段（USER/ADMIN） | L1 | → **RBAC + 数据权限**（M-A） |
| 票务下单 | `@Scheduled(60s)` 扫表超时 + 状态 CAS（pay/cancel/expire/refund 全条件更新）+ `user_session_quota` 原子配额 + `V53` 并发加固 | **L3** | → **延迟队列 + 幂等键 + 压测报告**（M-B） |
| 歌单 | 全量替换 PUT + 顺序重排 + 软删 | L2 | 保持 |
| 搜索 | `song.title` / `band.name` 两列 LIKE | L1 | → **别名 + ngram FTS + 归一化**（M-E） |
| 评论 | CRUD + 软删 | L1 | 保持（够用） |
| 收藏/歌单 | 关联表 + 唯一索引 | L1 | 保持 |
| 开售提醒 | 订阅表 + 定时扫描（0 条订阅） | L2 | → **通知中心**（M-F） |
| AI 助手 | SSE 流式 + **15 个工具**（身份闸门：非管理员只见 7 个只读）+ 事实预取 + 确认抢占 + 审计 | **L3** | → 工具扩展 + 数据体检（保留亮点） |
| 管理后台 | 5 个面板，均为表格 CRUD | L1 | → **报表 + 导出**（M-G） |
| 媒体 | `public/img` 静态文件，手工放置 | L0 | → **上传/压缩/裁剪流水线**（M-D） |

**有 2 个 L3（票务、AI），这是你的底子；再补 5 个 L3，就稳稳是毕设难度。**

## 2. 七个硬核模块

每个模块统一给：**现状 → 做什么 → 技术点（答辩会被问的）→ 可量化证明 → 工作量**。

### M-A 细粒度权限（RBAC + 数据权限）

**现状**：`user.role` 一个字段，`USER` / `ADMIN`。所有 `/admin/**` 一把梭，没有"内容审核员""运营"这类中间角色。

**做什么**

```sql
-- V56__rbac.sql
CREATE TABLE `role`            (`id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT, `code` VARCHAR(30) NOT NULL UNIQUE, `name` VARCHAR(50) NOT NULL, `builtin` TINYINT NOT NULL DEFAULT 0);
CREATE TABLE `permission`      (`id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT, `code` VARCHAR(50) NOT NULL UNIQUE, `name` VARCHAR(50) NOT NULL, `module` VARCHAR(30) NOT NULL);
CREATE TABLE `role_permission` (`role_id` BIGINT UNSIGNED NOT NULL, `permission_id` BIGINT UNSIGNED NOT NULL, UNIQUE KEY `uk` (`role_id`,`permission_id`));
CREATE TABLE `user_role`       (`user_id` BIGINT UNSIGNED NOT NULL, `role_id` BIGINT UNSIGNED NOT NULL, UNIQUE KEY `uk` (`user_id`,`role_id`));
```

- 后端：自定义注解 `@RequirePerm("song:update")` + 拦截器/AOP 校验；
- **数据权限**：同一接口按角色收窄可见数据（如"运营只能改自己负责乐队的内容"）。实现为「权限上下文 → 动态拼 SQL 条件」（`Specification` 或 `@Query` 白名单拼接），不是硬编码 if；
- 前端：路由 meta 带权限码，菜单按权限渲染；无权限走 403 页（不是白屏）。

**已有可复用能力（别重造）**

本项目已经实现 **`user.token_version`（V55）**：封禁/权限变更时 +1，过滤器比对版本号，旧令牌立即失效。
RBAC 的角色变更可以直接沿用同一机制——改完 `user_role` 后把 `token_version + 1` 即可，不需要再设计一套权限版本号。

**技术点（会被追问）**
1. 为什么不直接用 Spring Security？—— 给两种做法对比：**推荐做法**（Spring Security + 方法级注解）vs **最小改动兼容做法**（自研 `@RequirePerm` + 拦截器），说明当前自研 JWT 过滤器下的改造成本；
2. 权限缓存与失效：角色变更后如何立刻生效（本地缓存 + 版本号 / 短 TTL）；
3. 数据权限怎么避免 SQL 注入（白名单字段 + 参数化）。

**可量化证明**：权限矩阵表（角色 × 权限 × 接口）+ **越权测试用例**（5 个角色 × 10 个接口，全部符合预期）。

**工作量**：后端 3 人日，前端 1.5 人日。

### M-B 库存一致性升级（轮询 → 事件驱动 + 压测）

**现状**（代码事实，已是不错的 L3 底子）
- `OrderService.expirePendingOrders()`：`@Scheduled(fixedDelay = 60_000)` 扫 `PENDING_PAYMENT` 过期单；
- 下单 / 支付 / 取消都用状态 CAS（`update ... where status = ?`）抢转换权，抢不到视为并发已处理；
- 配额表 `user_session_quota` 做限购，取消时回滚库存。

**要做**

1. **超时释放改延迟队列**：Redis `ZSET`（score = 到期时间戳）或 RabbitMQ 延迟插件替代 60 秒轮询；
   - 可讲的取舍：轮询最长 60s 延迟、扫表随数据增长变慢、突发流量下给 DB 增压力；延迟队列精确到期、O(logN)；
   - **当前部署现实**：演示机是 2 核 4G、没有 Redis。落地顺序建议
     ① 先做「进程内延迟调度」（`ScheduledExecutorService` + 到期队列，重启会丢 → 用现有 60s 扫描兜底）；
     ② 再上 Redis ZSET 版本做对比实验；③ 报告里对比三种方案的延迟分布与 DB 压力，**"为什么不上 MQ"本身就是加分项**；
2. **幂等令牌**：下单接口支持 `Idempotency-Key`，重复提交返回同一订单（防连点 / 网络重试）；
3. **压测**：`k6` 或 `JMeter` 对 `POST /orders` 做 200 / 500 并发，验证 **超卖 0、超时释放准确、P95 < 500ms**；
4. **降级**：Redis 不可用时回落现有轮询 —— 这个"降级设计"本身就是加分点。

**技术点**
- 乐观锁 / 悲观锁 / 分布式锁在同一行库存上的 QPS 与失败率差异；
- 延迟队列的可靠性（消息丢失 → 补偿扫描兜底）；
- 幂等键设计（用户 + 场次 + 票档 + 时间窗）。

**可量化证明**：压测报告（并发数 - 成功率 - 平均/P95 - 超卖数），改前改后对比表。

**工作量**：后端 4 人日 + 压测调优 2 人日。

### M-C 候补名单与自动释放通知

**现状**：无。售罄就是死路。

**做什么**
- 表 `waitlist(id, user_id, session_id, ticket_type_id, quantity, status, created_at)`，唯一键防重复排队；
- 售罄时前端显示「加入候补」，入队（`WAITING`，位置可按 id 计算）；
- 有人取消/退款释放库存 → **按队列顺序**通知第一位（限时 15 分钟优先购买权），超时自动让给下一位；
- 管理端可见候补队列长度与转化率。

**技术点**
- 队列公平性（FIFO vs 会员优先）与"通知已发未购买"的过期处理；
- 状态机 `WAITING → NOTIFIED → PURCHASED / EXPIRED`，避免"通知了但库存被别处买走"的双重占用（需要预留计数 `reserved`，`available = total - sold - reserved`）；
- 复用 M-B 的延迟队列做候补超时。

**可量化证明**：状态机图 + 3 个并发场景测试（两人同时候补释放、通知超时、退款循环释放）。

**工作量**：后端 4 人日，前端 2 人日。

> 这是**业务复杂度最高**的模块：库存、队列、通知、超时四者交织，答辩非常好讲。

### M-D 媒体处理流水线（上传 / 压缩 / 裁剪）

**现状**：图片手工放进 `frontend/public/img`，后端零上传能力。最典型的"毕设缺失模块"。

**做什么**
- 表 `media_asset(id, owner_id, kind, path, width, height, size, mime, sha256, created_at)`；
- 接口：`POST /admin/media/upload`（multipart）、`GET /media/{id}`；
- **校验**：扩展名白名单 + **魔数校验**（防改后缀）+ 尺寸上限 + 单用户配额；
- **处理**：等比压缩（>1920px 缩到 1920）、生成缩略图（320px）、按用途裁剪（海报 3:4 / 横幅 16:9）；
- **存储**：本地目录 + 静态资源映射（毕设够用），用 `StorageService` 接口 + 本地实现，说明可替换为 OSS/MinIO；
- **安全**：随机文件名（sha256 前 16 位）、禁止路径穿越、`X-Content-Type-Options: nosniff`。

**技术点**
- 图片库选型（Thumbnailator / ImageIO / libvips）的内存与 CPU 开销；
- 大文件上传的内存控制（流式处理，不要 `byte[]` 全读）；
- 幂等：同 sha256 秒传去重；
- 私密图（用户回忆的照片）的鉴权访问（签名 URL 或 controller 代理）。

**可量化证明**：一张 4MB 手机照片 → 处理耗时、输出体积、缩略图尺寸的实测表。

**工作量**：后端 3 人日，前端 2 人日。

### M-E 检索：跨语言别名 + ngram FTS

**现状**：`LOWER(song.title) LIKE '%kw%'` + `LOWER(band.name) LIKE`，无 FULLTEXT，无别名表。

**做什么**
- 表 `entity_alias(entity_type, entity_id, lang, value, normalized)`；
- 表 `search_doc(entity_type, entity_id, lang, content, normalized)` + `FULLTEXT(normalized) WITH PARSER ngram`；
- 归一化管线：NFKC → 去中点/空白 → 片假名转平假名 → 罗马字转写 → 小写；中文可加拼音（`pinyin4j`）；
- 三级兜底：精确匹配 → ngram 全文 → 编辑距离（仅短串）。

**技术点**
- `ngram_token_size` 取值对召回/精度的影响（中文常用 2）；
- 日文长音符「ー」的归一化坑（不能直接删，要先折叠再处理）；
- 得分融合权重怎么定（10 条人工标注小规模调参即可，不需要大实验）。

**可量化证明**：50 条多写法查询（日文/罗马字/中文/简称）改造前后 **命中数** 对比 + 平均响应时间。

**工作量**：后端 4 人日，前端 1 人日。

### M-F 通知中心（站内信 + 实时推送）

**现状**：有 SSE 流式聊天，但没有"站内通知"；开售提醒只有表没有推送通道（0 条订阅）。

**做什么**
- 表 `notification(id, user_id, type, title, body, link, read_at, created_at)`；
- 触发源：开售提醒、候补通知、订单状态变更、审核结果；
- 推送：SSE（复用现有流式基建）或 WebSocket；前端顶栏铃铛 + 未读数 + 通知列表页；
- 多端一致性：已读状态同步（同一账号多标签页）。

**技术点**
- SSE vs WebSocket 的取舍（单向通知用 SSE 更简单，且已有基建）；
- 连接管理（心跳、断线重连、按用户维护 emitter 集合，防内存泄漏）；
- 离线补偿（不在线 → 落库，上线拉未读）。

**可量化证明**：100 个模拟连接下的推送延迟、断线重连成功率。

**工作量**：后端 3 人日，前端 2 人日。

### M-G 报表与导出（管理端）

**现状**：`GET /admin/stats/overview` 一个概览，无趋势、无导出。

**做什么**
- 销售趋势（按日/周/场次/票档聚合）、退款率、候补转化率、歌单覆盖率等运营指标；
- **Excel 导出**：订单明细、场次报表（EasyExcel 流式写，10 万行不 OOM）；
- 管理端新增「报表」标签页，图表用 ECharts（或轻量 SVG 自绘，避免引大依赖）。

**技术点**
- 聚合 SQL 的索引设计（时间范围 + 状态 + 场次）；
- 流式导出 vs 全量查内存（`SXSSFWorkbook` / EasyExcel）；
- 大报表异步化（生成任务 + 下载令牌），并说明何时该升级。

**可量化证明**：导出 5 万行订单的耗时与内存峰值（改前 OOM / 改后稳定）。

**工作量**：后端 3 人日，前端 2 人日。

## 3. 三项非功能底座（让系统"像企业级"）

| 项 | 做什么 | 技术点 | 工作量 |
|---|---|---|---|
| **缓存** | 热点（演出列表、歌曲详情、乐队页）加 Caffeine 本地缓存；写操作按 key 精确失效；缓存空值防穿透 | 一致性策略、TTL 抖动防雪崩、命中率统计 | 2 人日 |
| **可观测** | `traceId` 贯穿（MDC）+ 结构化日志 + 慢接口告警（>500ms）+ `/actuator/metrics` | 日志切面、指标埋点、慢 SQL 定位 | 2 人日 |
| **测试与质量** | 后端集成测试 + 前端 Vitest + Playwright；`jacoco` 覆盖率报告 | 测试分层、E2E 稳定性（防 flaky） | 持续 |

> **缓存建议 Caffeine 而非 Redis**：单机部署下零运维、性能更好；要讲"分布式缓存"再加 Redis 并说明一致性取舍。**技术选型要有理由，不是"用了新技术"就算深。**
>
> ⚠️ 演示机 2C4G（MySQL + 后端已占 2.3G），**Caffeine 必须设 `maximumSize` 与权重上限**，
> 否则"加了缓存反而 OOM"会成为答辩现场最难答的问题。

## 5. 六个迭代（每迭代 2~3 周）

| 迭代 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| **I1** | M-A 权限 + 非功能底座（traceId / 日志） | 权限矩阵 + 越权测试 | 无 |
| **I2** | M-B 库存一致性（延迟队列 + 幂等 + 压测） | 压测报告 v1 | I1 |
| **I3** | M-D 媒体处理 + M-G 报表导出 | 上传链路 + 导出性能数据 | I1 |
| **I4** | M-E 检索（别名 + ngram） | 检索对比表 | I1 |
| **I5** | M-C 候补 + M-F 通知中心 | 状态机 + 实时推送 | I2、I3 |
| **I6** | 缓存优化 + 覆盖率补齐 + 架构图/文档 | 完整交付 | 全部 |

## 6. 怎么"证明"它够难（答辩 / 简历的关键）

代码量是给外行看的，**老师与面试官看的是这四样**：

1. **压测报告**（M-B）
   - 表格：并发 100 / 200 / 500 下的 QPS、P50 / P95 / P99、错误率、超卖数；
   - 改前（轮询、无幂等）vs 改后（延迟队列、幂等）对比；
   - 结论一句话："500 并发下零超卖，P95 420ms"。

2. **技术选型对比表**（每个 L3 模块一张）
   - 例：延迟队列 —— `@Scheduled` / Redis ZSET / RabbitMQ 延迟插件 / RocketMQ 四行对比，给结论与放弃理由；
   - 最能体现"你在做工程决策，而不是抄教程"。

3. **架构图与状态机图**
   - 分层架构图（controller-service-repository + 横切：鉴权、日志、缓存）；
   - 订单状态机、候补状态机（`mermaid` 写进 docs，或 draw.io 导 PNG）。

4. **测试与覆盖率**
   - 后端 `jacoco`（目标 ≥ 55%，核心 service ≥ 70%）；
   - 前端单测 82 例 + E2E 18 条（已有），新模块同步补用例；
   - **越权测试集**：5 角色 × 10 接口的期望结果表。

## 8. 不要做的事（伪深度，纯浪费时间）

| 伪深度 | 为什么没用 |
|---|---|
| 再加 10 张实体表（全是 CRUD） | 表数量不是难度，**表之间的关系与约束**才是 |
| 堆 8 个前端列表页 | 页面数量不体现深度，**交互复杂度与性能**才体现 |
| 引入 Redis / MQ 但只当 KV 用 | "用了分布式组件"≠"解决了分布式问题"，一句"为什么用它"就问穿 |
| 单机跑 Docker + K8s | 负分项（复杂度换不来收益），Docker Compose 足够 |
| 加个"AI 大模型"却不做工程约束 | 调 API 不算深度，**超时 / 降级 / 审计 / 权限 / 成本**才是 |
| 照抄开源项目换皮 | 一问架构就开始"这个模块是引入的库"，直接崩 |

## 9. 三句话总结

1. **体量已够**：16.4k 行（后端 8.2k + 前端 8.2k）、18 张业务表、61 个接口，缺的是 L3 模块而不是行数。
2. **补 5 个 L3 就到毕设上限**：RBAC 数据权限、库存一致性（延迟队列 + 压测）、候补状态机、媒体流水线、跨语言检索；加上已有的票务并发与 AI 编排，共 7 个。
3. **难度靠四样东西证明**：压测报告、选型对比表、架构与状态机图、覆盖率与越权测试——**代码量只是入场券**。

## 10. 落地可行性：模块 × 环境依赖

> 这一节是给"明天就要动手"用的。方案里很多模块默认有 Redis / MQ / 大内存，
> 而当前演示环境是 **2 核 4G、无 Redis、无 MQ、无 Ollama**。先对照再排期，避免做一半发现跑不起来。

| 模块 | 运行依赖 | 当前环境是否满足 | 处理方式 |
|---|---|---|---|
| M-A 权限 | 无（纯 DB + 内存缓存） | ✅ | 直接做 |
| M-B 压测 | 压测机（k6/JMeter）可独立于演示机 | ✅（本地压） | 直接做，报告本地跑 |
| M-B 延迟队列（Redis 版） | Redis（约 100MB 内存） | 🟡 4G 内存可挤，但要另起进程 | 先做进程内版，Redis 版作为对比实验 |
| M-C 候补 | 依赖 M-B 延迟队列 + 通知通道 | 🟡 | 排在 M-B 之后 |
| M-D 媒体处理 | 磁盘（250G 够）+ **内存**（图片解码） | 🟡 4G 下必须限制并发 1~2、单图 ≤ 10MB | 流式处理 + 队列串行 |
| M-E 检索 | MySQL 8 自带 ngram FTS | ✅ | 直接做 |
| M-F 通知中心（SSE） | 长连接占线程/内存 | 🟡 单机可支撑百级连接，需设上限 | 设 `maxConnections`，超限降级为轮询 |
| M-G 报表导出 | 内存（EasyExcel 流式可控） | ✅ | 直接做，5 万行内不成问题 |
| 缓存（Caffeine） | 内存 | 🟡 必须设 `maximumSize` | 先只缓存"演出列表 + 歌曲详情" |

**结论**：7 个模块里 **5 个可以直接做**，2 个（延迟队列、媒体处理）需要先降级实现再谈对比实验。
排期时把"降级版"写进里程碑，比事后解释"为什么没做完"更好看。
