## 1. 一句话需求

一个 MyGO!!!!/Ave Mujica 主题的粉丝向平台：**粉丝**能浏览乐队资料、在线听歌（官方音源外链）、查看演出日程、购买演唱会门票（模拟支付）；**管理员**能管理歌曲库、发布演出与场次、管理订单、查看销售数据。

## 2. 参照产品分析

| 参照 | 借鉴点 |
|---|---|
| [Bestdori!](https://bestdori.com)（社区数据库站，开放 API） | 歌曲库的结构：单曲/专辑、乐队、成员、MV 链接、试听音源的元数据组织方式；数据可参考其公开 API |
| [hina-is](https://github.com/ahmadyasser72/hina-is)（BanG Dream 粉丝站） | 粉丝站整体形态：从社区 API 拉数据 → 本地展示；版权免责声明写法（学习用） |
| MyGO!!/Ave Mujica 官网 | 演出日程页（Live 列表：日期、场馆、开演时间、票价档）；唱片 Discography 页 |
| setlist.fm | 演出曲表（Setlist）档案：每场演出的曲目顺序记录 |
| 大麦网/票务系统 | 购票流程：演出 → 场次 → 票档（价位/库存）→ 下单 → 支付 → 出票/退票；**防超卖**是经典后端考点 |
| 网易云音乐 Web 版 | 播放器交互：底部全局播放条、播放队列、收藏、歌单 |

## 3. 用户与角色

## 5. 第一版明确不做（防止烂尾）

- ❌ 不托管/上传任何受版权保护的音频文件（只做外链：官方 MV 的 B 站/YouTube embed、官方试听片段）——同时页脚加"粉丝自制、非官方"免责声明
- ❌ 不做真实支付（模拟支付接口，重点在订单状态机与事务）
- ❌ 不做选座（座位图复杂度高，P2 之后再议，第一版按票档计数）
- ❌ 不做实时聊天、弹幕、第三方登录
- ❌ **不做通用爬虫系统**（数据获取走第 5.1 节的导入策略）

### 5.1 内容与数据来源策略（照片/视频/基础数据从哪来）

| 内容 | 策略 | 说明 |
|---|---|---|
| 歌曲/专辑/成员**基础数据** | **一次性导入脚本**（scripts/ 下）：调用 Bestdori 公开 API 拉取歌曲列表、乐队、成员元数据 → 写入 MySQL | 是开发工具不是产品功能；跑一次入库，之后后台可手工编辑。避免手录几十首歌 |
| **封面/海报等图片** | 手动收集少量（几十张以内）存本地 `frontend/public/assets/` 或对象存储；数据量大的卡面类**热链 Bestdori CDN 的公开资源 URL**（库存 url 进库，不落盘） | 不做批量抓取；个人学习范围风险可控，公开部署前再评估 |
| **MV/视频** | B 站官方 MV 的 **iframe embed 外链**，存 `mv_url` 字段 | 零存储、零版权风险，播放体验由平台保证 |
| **音频试听** | 不托管音源；用官方试听外链或只提供 MV 跳转 | 红线，不做变通 |
| 导入失败兜底 | 后台歌曲/演出 CRUD 本来就是 P0——导入脚本只负责"省手录"，缺的数据人工补 | 不为爬数据建子系统 |

> 原则：**凡是可以用"外链 + embed + 一次性导入"解决的，都不写爬虫。**爬虫作为独立小工具（可选 P2）单独评估，不进主项目。

## 6. 核心数据模型

> ~~草案~~ → **字段级定稿见 [docs/05-数据库设计.md](05-数据库设计.md)**（13 张表 + 订单/场次状态机 + 9 条业务规则）。下方为概览：

```
user            (id, username, password_hash, nickname, role, status, created_at, updated_at, is_deleted)
song            (id, title, band, album_id, release_date, cover_url, audio_url, mv_url, tags, duration, created_at, ...)
album           (id, name, band, cover_url, release_date, ...)
member          (id, name, band, cv, position, avatar_url, intro, ...)
live_event      (id, title, band, description, poster_url, venue, status, created_at, ...)
live_session    (id, event_id, start_time, status, ...)          # 场次
ticket_type     (id, session_id, name, price, total_stock, sold_count, ...)   # 票档
ticket_order    (id, user_id, session_id, ticket_type_id, quantity, amount, status, order_no, pay_deadline, ...)
favorite        (id, user_id, target_type, target_id, ...)
playlist        (id, user_id, name, ...)
playlist_item   (id, playlist_id, song_id, sort, ...)
setlist_item    (id, session_id, song_id, order_no, ...)
comment         (id, user_id, target_type, target_id, content, ...)
```

关键约束：`ticket_order` 下单时在**同一事务**内校验并扣减 `ticket_type` 余票（`total_stock - sold_count >= quantity`），防止超卖——这是本项目最大的技术亮点，后期可演进为乐观锁/Redis 方案对比。

## 7. API 概览

> **字段级接口规格见 [docs/06-接口设计.md](06-接口设计.md)**（统一响应、错误码表、每个接口的入参/出参/错误场景）。

```
POST /auth/register   POST /auth/login
GET  /songs?band=&album=&keyword=&page=      GET /songs/{id}
GET  /events?status=&page=                   GET /events/{id}    # 含场次与票档
POST /orders        {sessionId, ticketTypeId, quantity}      # 登录态
GET  /orders/my     PATCH /orders/{id}/cancel
GET  /favorites     POST /favorites      DELETE /favorites/{id}
管理端：POST/PUT/DELETE /admin/songs|/admin/events|/admin/sessions|/admin/ticket-types
        GET /admin/orders   PATCH /admin/orders/{id}/refund
        GET /admin/stats/overview
```

统一响应 `{code, message, data}`；错误码：400 参数 / 401 未登录 / 403 无权限 / 404 不存在 / 409 库存不足或状态不允许。

## 9. 用户旅程走查（发现需求缺口的方法）

> 清单是平铺的，走查才有场景感。三条旅程走一遍，缺口记在末尾。

### 旅程 A：游客（未登录）
打开首页 → 看到近期演出海报和新曲 → 点进歌曲详情 → 点播放 → **缺口①**：不能直接 404/静默失败，应弹登录引导框（"登录后即可播放"）→ 注册 → 登录 → 回到原页面继续播放（**缺口②**：登录后要跳回来源页，不是统一跳首页）。

### 旅程 B：注册用户（核心）
听歌 → 收藏 → 看演出日历 → 点开感兴趣的 Live → 选场次 → **缺口③**：票档要显示"余票紧张/已售罄"状态徽标 → 下单 → **缺口④**：订单详情页要有支付倒计时（15:00 递减），不是只躺在订单列表里 → 支付成功 → 看到电子票凭证（场次+票档+数量+订单号）→ 演出结束后可在"往期演出"里看 Setlist。

### 旅程 C：管理员
登录后台 → 新建演出（标题/海报/简介）→ 配场次（时间/场馆）→ 配票档（价格/库存）→ 发布开售 → 用户购票 → **缺口⑤**：订单管理要能按状态/演出/用户筛选 → 处理退款（回滚库存）→ 演出结束 → 看板核对销量与上座率 → 录入 Setlist。

### 走查发现的补充功能点

| 优先级 | 功能点 | 来源 |
|---|---|---|
| P1 | 全局搜索（顶部搜索框：歌曲 + 演出聚合结果） | 缺口①场景延伸 |
| P1 | 登录引导弹窗 + 登录后跳回来源页 | 缺口①② |
| P1 | 票档售罄/紧张状态徽标 | 缺口③ |
| P1 | 订单详情页 + 支付倒计时 + 电子票凭证页 | 缺口④ |
| P1 | 播放失败兜底（外链失效时显示"前往 B 站观看"） | 健壮性 |
| P1 | 空态/404 页面设计（无收藏、无订单时的引导文案） | 健壮性 |
| P2 | 演出开售提醒（站内消息） | 旅程 B 延伸 |

## 10. 验收标准示例（Given / When / Then）

**购票防超卖**：
- Given 某票档余票 1 张，When 两个用户同时下单 1 张，Then 恰好一个成功（200）一个失败（409 库存不足），`sold_count = total_stock`。

**订单超时**：
- Given 用户创建订单未支付，When 超过 15 分钟，Then 订单状态变为已取消，对应票档余票恢复。

**权限**：
- Given 未登录，When 调用 POST /orders，Then 返回 401。
- Given 普通用户，When 访问 /admin/*，Then 返回 403。

## 12. AI 助手模块（Ollama 本地模型）

> 优先级 P1（排在 M7，主线闭环优先）。底座已定：**Ollama + qwen3:8b**（2026-10 已下载至本机）。

### 12.1 为什么用本地模型

- 零 API 费用、零网络依赖，数据不出本机（站内数据注入 prompt 没有隐私顾虑）
- 技术卖点：SSE 流式输出 + 上下文注入（轻量 RAG），是简历上"会接 AI 能力"的实证
- 代价：响应慢于云 API（4060 Laptop 约 20~40 token/s），对话要控制上下文长度

### 12.2 三个功能的设计

| 功能 | 数据流 | 示例 |
|---|---|---|
| 站内知识问答 | 用户问题 → 后端按关键词查 MySQL（歌曲/成员/演出表）→ 把查询结果注入 system prompt → 模型作答，标注"数据来自本站" | "MyGO 的第一张单曲是什么？" |
| 歌曲推荐 | 用户描述心情/场景 → 后端按标签/乐队捞 10 首候选 → 模型生成带理由的推荐列表 | "想听适合深夜循环的" |
| 购票咨询 | 实时注入演出场次/票档余票/用户订单状态 → 模型解答并附购票入口指引 | "这周六的 Live 还有票吗？" |

**共同约束**：助手只回答与站点相关的问题（system prompt 限定边界）；涉及库存/订单的回答必须以注入的实时数据为准，不允许模型凭记忆编造；回答末尾附数据时间戳。

### 12.3 技术实现要点

- 后端：Spring Boot 通过 **OpenAI 兼容 API**（`http://localhost:11434/v1/chat/completions`）调用 Ollama，流式响应用 **SSE** 推给前端
- 前端：右下角悬浮助手窗，流式打字效果；会话历史仅存前端（localStorage），不建后端会话表（降低复杂度）
- 配置：模型名、API 地址走 `.env`/`application.yml`，`.env.example` 提供 `OLLAMA_BASE_URL` 占位
- 降级：Ollama 服务不可达时，助手入口显示"AI 助手离线"并降级为常见问题 FAQ 列表——**不能因为 AI 挂了影响主站**

### 12.4 验收标准示例

- Given Ollama 运行中，When 用户提问"MyGO 有哪些成员"，Then 流式返回站内成员数据且标注来源。
- Given 某场次余票 0，When 用户问"还有票吗"，Then 回答"已售罄"而非臆测。
- Given Ollama 未启动，When 用户打开助手，Then 显示离线提示，主站其他功能不受影响。
