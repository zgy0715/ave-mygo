# 12 · 前端提示词：小灯助手升级（界面重做 + 运营能力融合）

> **修订说明（2026-10-31 晚，v2）**：本文取代 `docs/11`（运营台独立页面方案）与 `docs/12` v1（纯界面升级）。
> 结论：**不新建"运营台"页面/标签**，运营能力直接长进悬浮球小灯里——一个入口、一个窗口。
> 后端接口零改动（`/api/v1/assistant/**` + `/api/v1/admin/agent/**` 都已就绪并测试通过）。

## 一、目标与原则

1. **一个入口**：右下角悬浮球小灯，全站唯一 AI 入口（游客/用户/管理员都是它）
2. **一个窗口**：同一个对话面板里，既能闲聊问答，也能下运营指令
3. **按身份给能力**：游客/普通用户只读问答；管理员多一个「运营」开关，打开后可调工具改数据
4. **写操作永远要确认**：确认卡片就在对话流里，不跳页、不弹二级窗
5. **不改后端**：所有能力基于现有两个接口，前端按角色路由

---

## 二、能力矩阵

| 身份 | 默认模式 | 能做什么 | 走哪个接口 |
|---|---|---|---|
| 游客 / 普通用户 | 问答模式（无开关） | 查歌、成员、演出、购票指引 | `POST /api/v1/assistant/chat/stream`（SSE） |
| 管理员 · 问答模式（默认） | 问答 | 同上，快（流式） | 同上 |
| 管理员 · 运营模式（手动开） | 运营 | 查数据 + 改数据（改 MV / 上下架 / 删场次 / 删演出），写操作出确认卡片 | `POST /api/v1/admin/agent/chat` → `POST /api/v1/admin/agent/confirm` |

**为什么运营模式要手动开而不是自动判断**：
- 自动判断（关键词/意图猜测）会误判，「帮我查一下这首歌」在两种模式下都合理；
- 运营模式一次请求内部跑多轮 LLM，20~60s，远慢于闲聊流式；默认开着会让普通问答变卡；
- 显式开关让用户知道"我现在是在动手模式"，也符合危险操作的心理预期。

开关只对 `user.role === 'ADMIN'` 渲染；切换模式**不清空当前消息**，消息里标记所属模式即可。

## 四、消息类型（一个消息流里容纳三种）

| 类型 | 来源 | 渲染 |
|---|---|---|
| `text` | 问答流式 / 运营回答 | 气泡 + 时间 + 复制；流式时末尾闪烁光标 |
| `tool` | 运营模式 | 灰色小字一行：`🔧 工具名 · 状态 — 摘要`；状态色：EXECUTED 灰、FAILED 红、PENDING 琥珀 |
| `confirm` | 运营模式写操作 | 琥珀卡片：动作标题 + 参数表 + [取消]/[确认执行]；决策后变绿/灰/红 |

消息结构：

```js
{
  id, role: 'user'|'assistant'|'system',
  mode: 'chat'|'ops',            // 该条属于哪个模式（切换不清空消息，靠它标记）
  text, at: Date.now(),
  streaming?: boolean,
  tools?: [{ name, status, summary }],
  pending?: { token, toolName, arguments, state: 'PENDING'|'EXECUTED'|'REJECTED'|'FAILED', result }
}
```

**确认卡片必须绑定自己的 pending 对象**（v1 的坑：用 `lastPending` 定位，多张卡片时会确认错目标）：

```vue
<button @click="confirm(pending, true)">确认执行</button>
```
```js
async function confirm(pending, approve) {
  if (!pending || pending.state !== 'PENDING' || confirming.value) return
  const data = await agentConfirm(pending.token, approve)
  pending.state = data.status
  pending.result = data.result || ''
}
```

## 五、调用路由（前端唯一需要判断的地方）

```js
const isAdmin = computed(() => auth.user?.role === 'ADMIN')
const opsMode = ref(false)          // 仅 isAdmin 时可开

async function send(text) {
  if (opsMode.value && isAdmin.value) {
    // 运营链路：非流式，20~60s，显示"小灯正在执行…"分步动画
    const data = await agentChat(text, conversationId)
    // data.type: 'reply' | 'pending_confirmation'
  } else {
    // 问答链路：SSE 流式（现有 chatStream）
  }
}
```

超时（v1 踩过的坑，务必照抄）：
```js
// api/agent.js —— 共享 axios 默认 10s，Agent 必须单独放开
export const agentChat = (message, conversationId) =>
  request.post('/admin/agent/chat', { message, conversationId }, { timeout: 180_000 })
export const agentConfirm = (token, approve) =>
  request.post('/admin/agent/confirm', { token, approve }, { timeout: 60_000 })
```

运营模式的等待体验（没有流式，别让用户干等）：
- 气泡内先显示「小灯正在执行…」+ 三点动画
- 若工具条目已返回（后端一次性返回，无法分步），直接整条渲染，不要假装分步
- 超过 20s 追加一行灰字「本地模型较慢，请稍候（约 30~60s）」

## 七、其余界面能力（问答/运营通用）

### P0
- 消息时间 `HH:mm` + 跨天「今天/昨天/日期」分隔

- 会话按人格持久化到 `sessionStorage`（最近 50 条，**不要存 token**）；恢复时保留 `mode` 与 `pending` 状态

- 长回复 >12 行折叠
- 轻量排版：`white-space: pre-wrap` 为主；若要加粗/列表，**先转义再替换**，禁止 `v-html` 渲染原始模型输出

## 八、边界与错误

| 场景 | 处理 |
|---|---|
| 管理员切到运营模式但 token 过期 | `request.js` 统一 401 处理；面板内提示重新登录 |
| 运营模式返回 50301（LLM 未启动） | 提示「运营模式需要 LLM 服务（Ollama）」+ 一键切回问答模式 |
| 确认返回 40902（已处理/过期/非本人） | 卡片标红「这次确认已失效，请重新下达指令」，保留参数供参考 |
| 执行失败（如删演出被未完成订单拦截） | 卡片标红，**原样展示后端 result**（例如"该演出存在待支付或已支付订单"），不要改写 |
| 非管理员误开运营（理论上不可能） | 403 时提示"需要管理员权限"并自动关掉开关 |
| 运营模式请求被关闭面板中断 | 请求无法取消（非流式）；回来后消息照常入列 |
| 播放条出现 | 保留现有避让逻辑，面板上移 |

## 十一、给实现者的三条提醒

1. **别做第二个入口**：运营能力就在小灯里，任何"管理端另开一页"的思路都是错的（v1 已走错一次）。
2. **确认卡片必须绑自己的 pending**：`@click="confirm(pending, true)"`，不要用 `lastPending` 之类的全局查找。
3. **问答走 SSE、运营走普通 POST**：两条链路超时/中断行为不同，运营链路不可取消（后端非流式），别在 UI 上假装能停。
