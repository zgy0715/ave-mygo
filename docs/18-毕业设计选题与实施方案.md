## 0. 一句话选题

> **《面向粉丝协作知识库的多源事实可信度评估与可溯源问答方法研究
> ——以 BanG Dream! 音乐演出档案为例》**

拆开说：**研究对象**是"多来源、会冲突、跨语言"的粉丝向事实数据；
**要解决的方法问题**是"如何判断一条事实可不可信、如何把它检索出来、如何让大模型只依据它回答"；
**载体**是已经跑起来的这个站（55 首曲目 / 6 场演出 / 23 个场次 / 本地 Ollama 助手）。

---

## 1. 先诊断：为什么现在的方向"不够深"

你手上的 `docs/17` 有 6 个里程碑、20 多张表，工程量够，但**评审需要的是"方法"而不是"功能"**。三问：

| 评审会问 | 17 号文档能答吗 | 缺什么 |
|---|---|---|
| **创新点在哪？** | ❌ 只能答"我做了一个知识库网站" | 需要一个能被检验的技术命题 |
| **工作量够吗？** | ✅ 表/接口/页面数得清 | 但工程量大 ≠ 技术深度 |
| **怎么证明有效？** | ❌ 只有"能跑通" | 需要**实验、数据、指标对比** |

**毕业设计的本质是把"做出来"变成"说清楚为什么这样做更好，并用数据证明"**。所以要补三样东西：

1. **一个可证伪的技术命题**（不是"我要做可信知识库"，而是"我提出 X 方法，它比 Y 基线在 Z 指标上好"）；
2. **一套构造好的实验数据**（gold set / query set / QA set）；
3. **一组对照实验 + 指标**（而不是"功能演示"）。

下面的方案就是按这个思路重排的。

## 2. 选题定位

### 2.1 三个研究问题（RQ）

| RQ | 问题 | 对应子系统 | 可量化指标 |
|---|---|---|---|
| **RQ1** | 同一字段存在多个冲突来源时，如何给出**可解释的可信度排序**？ | 数据可信层 | NDCG@k、冲突检出 F1、人工一致性 κ |
| **RQ2** | 日文原名 / 罗马字 / 中文译名 / 简称混用时，如何**准确召回**同一实体？ | 检索对齐层 | Recall@1、Recall@5、MRR |
| **RQ3** | 如何约束大模型**只依据可信事实作答**，并在依据不足时拒答？ | 问答生成层 | 引用准确率、拒答正确率、幻觉率 |

三个 RQ 是一条直线：**可信 → 找得到 → 说得对**，正好是"知识库"的三层，不是三个孤立功能。

### 2.2 三个创新点（答辩时直接背这三条）

1. **字段级多源可信度模型（Field-level Trust, 下称 FLT）**
   现有做法是给"一条记录"打一个"已核实"标签。本文把核验粒度下沉到**字段**，提出组合"来源权威度 × 时效衰减 × 交叉一致度 − 冲突惩罚"的打分函数，并给出多来源冲突的自动检测与消解规则。**可证伪**：相比"按录入时间排序"的基线，在人工标注的 gold set 上 NDCG@5 提升 ≥ 15%。

2. **跨语言实体别名对齐与混合检索**
   针对日文原名（みそしる）/ 罗马字（Misoshiru）/ 中文译名（迷星叫）/ 简称混用导致召回失败的问题，设计"归一化管线 + 别名字典 + ngram 全文索引 + 编辑距离兜底"的混合检索。**可证伪**：在自建 query set 上 Recall@5 相对现状 LIKE 匹配提升 ≥ 30%。

3. **可信度约束的检索增强问答（Trust-constrained RAG）**
   把 RQ1 的可信度分数作为检索排序依据注入大模型上下文，并强制结构化输出引用；当最高可信度低于阈值或证据不足时**主动拒答**。**可证伪**：相比现状（固定预取 + 无引用），引用准确率 ≥ 85%、无依据问题拒答正确率 ≥ 80%、幻觉率下降 ≥ 40%。

> 这三条都能写成"提出方法 → 实验证明 → 消融分析"的标准论文结构，而且**数据和实验完全在你手里**，不依赖外部数据集。

### 2.3 与"已有做法"的差异（写进相关工作一章）

不要凭空引用文献，按**技术路线类别**对比即可，具体文献等你开题前用 CNKI/IEEE 检索补齐：

| 类别 | 典型做法 | 本文差异 |
|---|---|---|
| 粉丝 wiki（如各类 Fandom） | 人工维护，来源以"引用块"形式挂在页面 | 本文把来源下沉到**字段级**并参与排序计算 |
| 通用知识图谱 | 实体-关系-属性，冲突靠人工仲裁 | 本文做**自动冲突检测 + 可信度打分**，适合小团队维护 |
| 通用 RAG 问答 | 向量召回 top-k → 拼接 → LLM 生成 | 本文在召回后加**可信度重排**，并强制"无依据拒答" |
| 现有站内助手（本项目 v2） | 正则命中成员类问题时**全量预取**注入 system prompt | 本文改为**按问题检索 top-k**，可扩展到全实体类型 |

> ⚠️ **学术诚信提醒**：论文里的参考文献必须自己检索、自己读、自己引。本文只给"检索方向"，不给编造的文献条目。

### 3.1 三层架构（论文第 4 章的主图）

```
┌──────────────────────────────────────────────────────────┐
│  L3 问答生成层  Trust-constrained RAG                     │
│     问题 → 意图识别 → 检索 top-k → 可信度重排 → 上下文注入 │
│     → 结构化输出 {answer, citations, insufficient}        │
├──────────────────────────────────────────────────────────┤
│  L2 检索对齐层  Alias & Hybrid Retrieval                  │
│     归一化管线 / 别名字典 / MySQL ngram FTS / 编辑距离兜底 │
├──────────────────────────────────────────────────────────┤
│  L1 数据可信层  Provenance & Trust                        │
│     source / fact_ref(字段级) / fact_conflict / T(f) 打分  │
└──────────────────────────────────────────────────────────┘
```

### 3.2 现状核实（哪些已有、哪些要新建）

| 层 | 现状（代码事实） | 毕设要做的 |
|---|---|---|
| L1 | 全库**无任何来源字段**，无 `source` 表；`agent_tool_calls` 只有 73 条 Agent 审计 | 新建 `source` / `fact_ref` / `fact_conflict` / `content_revision`（见 17 号 §3） |
| L2 | 搜索函数只做 `LOWER(song.title) LIKE` + `LOWER(band.name) LIKE`；**无 FULLTEXT 索引**；**无别名表**；成员表有 `name_ja`/`name_romaji` 但搜索未使用 | 建 `entity_alias` + `search_doc`（ngram FTS）+ 归一化工具类 |
| L3 | `AssistantStreamService`：**仅当正则命中成员类问题**时 `prefetch("list_members")` 全量注入；无引用、无拒答、无检索排序；LLM 为本地 Ollama + `MarkdownStripper` | 改成"任意问题 → 检索 top-k 事实块 → 可信度重排 → 强制引用" |

## 4. 三个研究点的详细设计

### 4.1 RQ1：字段级多源可信度模型（FLT）

#### 4.1.1 数据模型（与 17 号 §3 一致，此处只列打分相关）

`source(kind, publisher, published_at, retrieved_at, trust)` + `fact_ref(entity_type, entity_id, field, source_id, status)` + 新增 `fact_conflict`：

```sql
-- V57__fact_conflict.sql
CREATE TABLE `fact_conflict` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `entity_type` VARCHAR(20) NOT NULL, `entity_id` BIGINT UNSIGNED NOT NULL,
  `field` VARCHAR(40) NOT NULL,
  `value_norm` TEXT NOT NULL COMMENT '归一化后的取值，用于判定是否等价',
  `source_id` BIGINT UNSIGNED NOT NULL,
  `detected_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `status` VARCHAR(20) NOT NULL DEFAULT 'OPEN' COMMENT 'OPEN/RESOLVED/IGNORED',
  `resolution` VARCHAR(200) NULL,
  PRIMARY KEY (`id`), KEY `idx_fact` (`entity_type`,`entity_id`,`field`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='字段级来源冲突';
```

#### 4.1.2 打分函数（论文公式就是它）

对事实 `f`（某实体的某字段），由来源集合 `S_f = {s1..sn}` 支撑：

```
T(f) = Σ_i  w(si) · ρ(Δt_i)  /  n     ×   (1 + α · agree(f) − β · conflict(f))
```

- `w(si)`：来源权威度权重，`OFFICIAL_SITE=1.0`、`OFFICIAL_X/YT=0.9`、`PRESS=0.7`、`FAN_WIKI=0.5`、`OTHER=0.3`；
- `ρ(Δt) = exp(−λ·Δt/365)`：时效衰减，`λ` 建议 0.3（一年衰减 ~26%），因为**音乐作品事实几乎不变**，衰减只用来压制过期信息（如已改期的演出）；
- `agree(f)`：有多少比例的来源给出**同一归一化取值**（0~1）；
- `conflict(f)`：是否存在互斥取值（0/1）；
- `α=0.3`、`β=0.5`：可调超参，写进消融实验。

**归一化**（判定"两个来源说的是不是同一件事"）：日期统一 `yyyy-MM-dd`；时长统一秒并容差 ±2s；文本去空格/全角半角/大小写；人名去「・」。

#### 4.1.3 冲突消解规则（工程实现，也是论文一个小节）

1. 若存在 `trust=1`（官方）来源 → 以官方值为准，其余标 `DISPUTED`；
2. 若多条官方来源冲突 → 取 `published_at` 最晚的一条，并在管理端告警；
3. 若全是社区来源 → 取多数票，票数相同则保留最旧值（保守原则）；
4. 任何冲突都**不静默覆盖**：写入 `fact_conflict`，前端在字段旁显示「来源冲突，待核验」。

#### 4.1.4 实验设计

| 项 | 内容 |
|---|---|
| 数据 | 55 首歌 × 4 字段（title/release_date/duration/album）+ 6 场演出 × 3 字段（title/venue/start_date）≈ **240 条事实** |
| 标注 | 每条人工找 1~3 个来源，标注"正确值"与"来源可信等级"；双人标注 30 条算 Cohen's κ（或单人隔周重测） |
| 基线 | B1：按录入时间排序；B2：按来源数量排序（票数） |
| 指标 | NDCG@3/@5（把"正确值来源"排在前列的收益）、冲突检出 P/R/F1（与人工判定的冲突对照） |
| 预期 | NDCG@5 相对 B1 提升 ≥ 15%；冲突检出 F1 ≥ 0.8 |

**消融**：分别去掉 `ρ`（时效）与 `agree`（交叉一致），看 NDCG 变化——证明每个因子都有用。

### 4.2 RQ2：跨语言别名对齐与混合检索

#### 4.2.1 归一化管线（用 Java 实现，放在 `search/Normalizer.java`）

处理顺序（顺序不能错）：

1. Unicode NFKC（全角→半角、`㍿` 类兼容字符归一）；
2. 去除所有空白与中点 `・·･`、连接符 `‐-ー`（**长音符单独处理**，见下）；
3. 片假名 → 平假名（`ァ-ヶ` → `ぁ-ゖ`，码位偏移 `-0x60`）；
4. 平假名 → 罗马字（训令式/赫本式二选一，**统一用一种**，建议赫本式）；
5. 罗马字转小写、去长音符号（`ō`→`o`）、`ou/oo` → `o`（可变体）；
6. 中文简体（如需，可用简化字表；本站在用中文时直接保留）。

> **坑点**：日文长音「ー」在片假名转罗马字时是"延长前一元音"，不能简单删除，否则「キラキラ」和「キラキラ—」会归一成不同串。建议在归一化阶段保留一个占位符再统一折叠。

#### 4.2.2 索引与检索策略（三级兜底）

```sql
-- V58__search_doc.sql
CREATE TABLE `search_doc` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `entity_type` VARCHAR(20) NOT NULL,
  `entity_id` BIGINT UNSIGNED NOT NULL,
  `lang` VARCHAR(10) NOT NULL,
  `content` VARCHAR(500) NOT NULL COMMENT '原始可读文本（用于展示）',
  `normalized` VARCHAR(500) NOT NULL COMMENT '归一化文本（用于匹配）',
  PRIMARY KEY (`id`),
  FULLTEXT KEY `ft_norm` (`normalized`) WITH PARSER ngram,
  KEY `idx_entity` (`entity_type`,`entity_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

检索打分（三级）：

```
score = 1.0 × exactMatch(normalized)          // 精确
      + 0.8 × ftScore(MATCH ... AGAINST)      // ngram 全文
      + 0.5 × (1 - editDistance/L)            // 编辑距离兜底（长度 ≤ 30 才用）
      + entityBoost(entityType)               // 歌曲 > 演出 > 场馆
```

**为什么不上向量检索**：数据量 300 条级，BM25/ngram 的可解释性更好，且"为什么召回这条"能直接写进论文；向量检索留作"未来工作"或作为对比基线之一（用 Ollama embedding + 内存索引，工作量 1~2 天，可作为加分项）。

#### 4.2.3 实验设计

| 项 | 内容 |
|---|---|
| query set | 每首歌构造 4 种写法（日文原名 / 罗马字 / 中文译名 / 简称或错拼）≈ **220 条 query**；再补 30 条成员与场馆 |
| 基线 | B0：现状 `LOWER(title) LIKE '%kw%'` |
| 指标 | Recall@1、Recall@5、MRR、平均响应时间（ms） |
| 预期 | Recall@5 ≥ 0.90（现状预计 < 0.5）；MRR 提升 ≥ 0.3 |
| 附加 | 记录 50 条"归一化前后"对照样例，写进论文附录（很能体现工作量） |

### 4.3 RQ3：可信度约束的检索增强问答

#### 4.3.1 管线（替代现有"正则 + 全量预取"）

```
用户问题
  → ① 意图/实体识别（轻量：别名字典最长匹配 + 关键词规则，不引 NER 模型）
  → ② 混合检索（RQ2）取 top-20 事实块
  → ③ 可信度重排（RQ1 的 T(f)）取 top-6
  → ④ 组装上下文（每条事实带 field / value / source / verifiedAt / T(f)）
  → ⑤ LLM 生成，强制 JSON 输出 {answer, citations[], insufficient}
  → ⑥ 后校验：citations 里的 entity/field 必须在 ④ 的上下文里出现过，否则整条丢弃并降级为"依据不足"
```

第 ⑥ 步是**工程上的防幻觉闸门**，也是论文里"为什么有效"的关键论据：不是靠 prompt 求模型老实，而是**输出结构可校验**。

#### 4.3.2 新增表（引用落库，便于追溯与统计）

```sql
-- V59__answer_citation.sql
CREATE TABLE `answer_citation` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `message_id` BIGINT UNSIGNED NOT NULL COMMENT 'agent_messages.id',
  `entity_type` VARCHAR(20) NOT NULL, `entity_id` BIGINT UNSIGNED NOT NULL,
  `field` VARCHAR(40) NULL, `source_id` BIGINT UNSIGNED NULL,
  `trust` DECIMAL(4,3) NULL,
  `verified` TINYINT NOT NULL DEFAULT 0 COMMENT '⑥ 后校验是否通过',
  PRIMARY KEY (`id`), KEY `idx_msg` (`message_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

#### 4.3.3 实验设计（这是论文第 6 章的主体）

| 项 | 内容 |
|---|---|
| QA 集 | **60 题**：成员 10 / 曲目 12 / 专辑 8 / 演出 10 / 组合查询 10（如"这两场都唱了哪些歌"）/ **无依据 10**（站内确实没有资料，如"某成员的生日是哪天"若库里没有） |
| 对照组 | **A 现状**（正则预取 + 无引用）· **B 普通 RAG**（检索但不做可信度重排、不强制引用）· **C 本文方法**（检索 + 可信度重排 + 强制引用 + 拒答） |
| 客观指标 | 引用准确率（引用的每条是否真的支撑该句，人工判定）、拒答正确率（无依据题被正确拒答的比例）、幻觉率（含无可支撑具体事实的句子占比） |
| 主观指标 | 5 位同学按 1~5 分评"答案可用性"（双盲：不告诉他们哪组是本文方法） |
| 预期 | C 组：引用准确率 ≥ 85%、拒答正确率 ≥ 80%、幻觉率 < 10%；相对 A 组幻觉率下降 ≥ 40% |

**消融实验**：C 去掉可信度重排 → C1；C 去掉后校验 → C2。用来证明"重排"和"闸门"各自贡献多少。

> **注意实验伦理**：只用站内公开数据，不涉及真实用户隐私；LLM 用本地 Ollama（模型由 `LLM_MODEL` 环境变量指定，**实验前必须固定 tag**，否则结果不可复现），不把数据发第三方，这一点可以写进论文"数据安全"小节，是加分项。

## 6. 数据与实验集构建（最花时间，也最值钱）

| 数据集 | 规模 | 构建方式 | 预计工时 |
|---|---|---|---|
| fact gold set | ~240 条事实 | 逐条找官方来源（官网 discography / 官方 X / 官方 YouTube），填 `source` + 正确值 | **8~12 天**（最重） |
| conflict set | 20 组 | 一半来自真实（不同来源不一致），一半人工构造（改一个值造冲突），用于测检出率 | 2 天 |
| alias set | ~260 条 query | 每实体 4 种写法；罗马字用赫本式统一，错拼集找 2 位同学各写一遍 | 3 天 |
| QA set | 60 题 + 标准答案 + 依据标注 | 自己出题，答案必须能在库里找到对应事实 | 3 天 |
| 标注一致性 | 30 条双人 | 找一位同学独立标注，算 κ（>0.6 可接受） | 1 天 |

**标注规范要写成文档**（附在论文附录）：什么算"同一事实"、什么算"有依据"、什么样的句子算"幻觉"。规范写得清楚，答辩时"数据怎么来的"就答得漂亮。

## 10. 风险与降级方案

| 风险 | 影响 | 降级方案 |

## 12. 一页纸摘要（可直接用于开题报告）

> 本项目面向粉丝协作维护的音乐演出资料库，研究**多来源冲突事实的可信度评估**与**可溯源问答**问题。
> 针对现有粉丝知识库"来源挂在页面级、冲突靠人工仲裁、跨语言检索召回低、大模型回答无依据"的问题，提出三点方法：
> （1）**字段级多源可信度模型 FLT**，以来源权威度、时效衰减、交叉一致度与冲突惩罚构成打分函数，并给出冲突检测与消解规则；
> （2）**跨语言别名归一化与混合检索**，融合 ngram 全文索引与编辑距离兜底，解决日文原名/罗马字/中文译名混用问题；
> （3）**可信度约束的检索增强问答**，以可信度重排检索结果并强制结构化引用，配合输出后校验实现"无依据拒答"。
> 系统基于 Spring Boot 3 + Vue 3 + MySQL 8 + 本地 Ollama 实现，已具备曲目、专辑、演出、场次、歌单、票务等业务模块。
> 实验在自建的 240 条标注事实、260 条查询与 60 题问答集上进行三组对照与消融，预期在 NDCG@5、Recall@5、引用准确率与幻觉率四项指标上相对基线取得显著提升。
