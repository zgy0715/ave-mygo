# 02 · 开发规范（企业级约定）

## Git 规范

### 分支模型（简化 GitHub Flow，适合单人/小团队）

```
main          # 始终可运行，只接受 PR 合入
└── dev       # 日常开发主线（可选，项目小可省略）
    └── feat/xxx   # 功能分支：feat/user-login, feat/order-list
    └── fix/xxx    # 修复分支：fix/login-token-expired
```

### Commit 信息（Conventional Commits）

```
<type>(<scope>): <简短描述>

类型：feat 新功能 | fix 修复 | docs 文档 | style 格式 | refactor 重构
     | test 测试 | chore 构建/杂项 | perf 性能
示例：feat(auth): 实现登录接口与 JWT 签发
```

- 一次 commit 只做一件事；描述用中文或英文均可，但**全程统一**。

## 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件/组件（前端） | PascalCase（组件）/ kebab-case（工具） | `UserCard.vue` / `use-auth.js` |
| 变量/函数 | camelCase | `getUserById` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 数据库表/字段 | 小写下划线，表名复数或单数全程统一 | `user_account` / `created_at` |
| 接口路径 | 全小写 kebab-case，资源名复数 | `GET /api/v1/orders/{id}` |

## 目录与代码约定

- **前后端完全分离**：`frontend/` 与 `backend/` 各自独立仓库式管理（同一 Git 库 monorepo 或分库，开工时定）。
- **API 版本化**：统一前缀 `/api/v1/`，为将来升级留空间。
- **统一响应结构**（后端必须遵守）：

```json
{ "code": 0, "message": "ok", "data": { } }
```

- **错误处理**：业务错误用 code 区分，不抛裸 500；参数校验在入口层（DTO）完成。
- **日志**：关键链路（登录、支付、写库）必须有日志，格式统一含时间/级别/traceId。

## 数据库规范

- 建表三要素齐全：`id`（自增主键）、`created_at`、`updated_at`（DATETIME，DEFAULT CURRENT_TIMESTAMP）。
- 禁止物理删除默认化：业务数据用 `is_deleted` 软删除标记（日志类数据除外）。
- 所有变更走 `sql/` 下的版本化脚本（`V1__init.sql`、`V2__add_order.sql`…），不在客户端手工改表。

## 敏感信息

- `.env`、密码、密钥**绝不入库**；每个工程提供 `.env.example` 占位模板。
