## 2. 主线定义

> **建设一个数据可信的 BanG Dream! 音乐与演出知识库，并让粉丝能围绕这些资料记录、探索自己的体验。**

三个"不做"，用来防止范围失控：

1. **不接真实支付**：购票永远是演练场，不涉及资金。
2. **不做通用社交**：没有私信、动态流、关注关系图谱；社区只围绕"资料更正"和"现场回忆"。
3. **不为了推荐而上复杂模型**：推荐先做可解释的关联规则（同专辑 / 同场次 / 同标签），不做向量召回。

## 3. 数据可信基座（P0，其余一切的前提）

这是整个主线的地基。**没有来源模型，"AI 附依据""审核更正""数据健康检查"三件事都做不了**。

### 3.1 来源表 `source`

```sql
-- V54__provenance.sql
CREATE TABLE `source` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `kind`          VARCHAR(32)  NOT NULL COMMENT 'OFFICIAL_SITE/OFFICIAL_X/OFFICIAL_YT/BILIBILI_OFFICIAL/FAN_WIKI/PRESS/OTHER',
  `url`           VARCHAR(500) NOT NULL,
  `title`         VARCHAR(200) NULL COMMENT '页面/推文标题',
  `publisher`     VARCHAR(100) NULL COMMENT '发布方，如 Bushiroad / 官方 YouTube',
  `published_at`  DATETIME     NULL COMMENT '原始发布时间',
  `retrieved_at`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '我们抓取/核验的时间',
  `trust`         TINYINT      NOT NULL DEFAULT 2 COMMENT '1官方 2官方媒体 3社区 4其他',
  `note`          VARCHAR(200) NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_url` (`url`(191)),
  KEY `idx_kind` (`kind`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='事实来源';
```

### 3.2 字段级核验表 `fact_ref`

关键设计：**核验粒度到「某实体的某个字段」**，而不是给整条记录打一个"已核实"。

```sql
CREATE TABLE `fact_ref` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `entity_type` VARCHAR(20) NOT NULL COMMENT 'SONG/ALBUM/EVENT/SESSION/MEMBER/BAND/TOUR',
  `entity_id`   BIGINT UNSIGNED NOT NULL,
  `field`       VARCHAR(40) NOT NULL COMMENT '如 release_date / duration / setlist',
  `source_id`   BIGINT UNSIGNED NOT NULL,
  `status`      VARCHAR(20) NOT NULL DEFAULT 'VERIFIED' COMMENT 'VERIFIED/UNVERIFIED/DISPUTED',
  `verified_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `verified_by` BIGINT UNSIGNED NULL COMMENT 'NULL=系统/脚本，否则管理员 id',
  `note`        VARCHAR(200) NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_fact` (`entity_type`,`entity_id`,`field`),
  KEY `idx_source` (`source_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='字段级来源核验';
```

**为什么要字段级**：`song.release_date` 可能来自官方 discography，而 `song.duration` 来自 B 站视频信息（可信度更低）。一个"已核实"标签会掩盖这种差异。字段级核验才能支撑前端展示「时长：4:06（来源：官方 MV 时长，2026-10-19 核验）」。

### 3.3 别名表 `entity_alias`

```sql
CREATE TABLE `entity_alias` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `entity_type` VARCHAR(20) NOT NULL COMMENT 'SONG/ALBUM/EVENT/MEMBER/BAND/TOUR/VENUE',
  `entity_id`   BIGINT UNSIGNED NOT NULL,
  `lang`        VARCHAR(10) NOT NULL COMMENT 'ja/zh/romaji/abbr/en',
  `value`       VARCHAR(200) NOT NULL,
  `normalized`  VARCHAR(200) NOT NULL COMMENT '小写 + 去空格/中点/全角半角归一，用于匹配',
  `is_primary`  TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_entity_value` (`entity_type`,`entity_id`,`lang`,`value`),
  KEY `idx_norm` (`normalized`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='实体别名';
```

**落地顺序**：先给 `SONG` + `MEMBER` 回填（55 + 12 条，人工可控），再给 `EVENT`/`ALBUM`。
`normalized` 用 Java 侧统一处理器：去空格、去「・」、全角转半角、`toLowerCase`。

> ⚠️ **事实红线提醒**：别名数据属于"粉丝向事实"，回填必须逐条对照官方 discography / 官方 SNS，**不允许凭记忆填**（这是本项目已发生过两次翻车的地方）。

### 3.4 变更历史 `content_revision`

```sql
CREATE TABLE `content_revision` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `entity_type` VARCHAR(20) NOT NULL,
  `entity_id`   BIGINT UNSIGNED NOT NULL,
  `action`      VARCHAR(20) NOT NULL COMMENT 'CREATE/UPDATE/DELETE/RESTORE',
  `diff_json`   JSON NOT NULL COMMENT '{"field":{"from":..,"to":..}}',
  `actor_type`  VARCHAR(10) NOT NULL COMMENT 'USER/ADMIN/AGENT/SYSTEM',
  `actor_id`    BIGINT UNSIGNED NULL,
  `source_id`   BIGINT UNSIGNED NULL COMMENT '本次修改依据',
  `reason`      VARCHAR(200) NULL,
  `created_at`  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_entity` (`entity_type`,`entity_id`,`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内容变更历史';
```

写入点只有两处：`Admin*Service` 的 update 方法 与 `AgentService` 的写工具执行后（后者已有审计，改为双写）。

### 3.5 配套接口（P0 阶段）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/facts/{entityType}/{entityId}` | 该实体的字段级来源列表 | 公开 |
| GET | `/api/v1/revisions/{entityType}/{entityId}` | 变更历史（分页） | 公开（字段级脱敏，不暴露操作者身份以外的隐私） |

**验收**

- 55 首歌的 `title` / `release_date` / `duration` 三条关键字段，`fact_ref` 覆盖率 ≥ 90%；
- 任一公开页面看到的"事实"，都能点到来源；
- 改一条数据的字段，`content_revision` 必产生一条 `diff_json` 记录。

## 4. 演出档案纵向闭环（M1，最优先）

目标：让「一场演出唱了什么、和上一场差在哪、这首歌还在哪唱过」这三问有答案。

### 4.1 场馆 / 城市 / 巡演

```sql
CREATE TABLE `city` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `name_zh` VARCHAR(50) NOT NULL, `name_ja` VARCHAR(50) NULL, `country` VARCHAR(30) NOT NULL DEFAULT 'JP',
  PRIMARY KEY (`id`), UNIQUE KEY `uk_zh` (`name_zh`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE `venue` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `name_ja` VARCHAR(120) NOT NULL, `name_zh` VARCHAR(120) NULL,
  `city_id` BIGINT UNSIGNED NOT NULL, `capacity` INT NULL, `official_url` VARCHAR(500) NULL,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`), UNIQUE KEY `uk_name_city` (`name_ja`,`city_id`), KEY `idx_city` (`city_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE `tour` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `band_id` SMALLINT UNSIGNED NOT NULL, `title` VARCHAR(150) NOT NULL,
  `kind` VARCHAR(20) NOT NULL COMMENT 'TOUR/ONE_MAN/FESTIVAL/EVENT',
  `start_date` DATE NULL, `end_date` DATE NULL, `official_url` VARCHAR(500) NULL,
  PRIMARY KEY (`id`), KEY `idx_band` (`band_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

改造现有两列：

```sql
ALTER TABLE `live_event`   ADD COLUMN `tour_id` BIGINT UNSIGNED NULL COMMENT '所属演出项目' AFTER `band_id`;
ALTER TABLE `live_session` ADD COLUMN `venue_id` BIGINT UNSIGNED NULL COMMENT '本场场馆（可覆盖 event.venue）' AFTER `event_id`;
```

**兼容策略**：`live_event.venue` 与 `live_session` 上不删列。新代码优先读 `venue_id`，为空时回退旧字符串。回填脚本按 `event.venue` 文本匹配 `venue.name_ja`，匹配不上的列入人工清单（预计 6 场演出对应 5~6 个场馆，一次就能清完）。

### 4.2 三个新页面 / 三个新接口

| 页面 | 路由 | 核心内容 | 依赖接口 |
|---|---|---|---|
| 场次详情 | `/sessions/:id` | 开演/开售时间、场馆+城市、本场歌单（含安可）、票档、同巡演其他场次切换 | `GET /sessions/{id}`（新）、`GET /events/sessions/{id}/setlist`（已有） |
| 巡演时间线 | `/tours/:id` | 各场次按日期排列，点开看该场歌单 | `GET /tours/{id}`（新）、`GET /tours/{id}/sessions`（新） |
| 歌曲现场足迹 | 歌曲详情页区块 | 这首歌被哪些场次唱过（可按乐队/年份过滤） | `GET /songs/{id}/live-appearances`（新） |

**歌单对比（M1 的核心体验）**

```
GET /api/v1/tours/{tourId}/setlist-compare
→ data: {
    sessions: [{sessionId, date, venue, songCount, encoreCount}],
    rows: [{songId, title, appearCount, bySession: {sessionId: orderNo|encore|absent}}]
  }
```
前端渲染成"曲目 × 场次"的矩阵表：出现打点、安可换色、缺席留空。**这是这个项目最有辨识度的一个页面**，比再加十张演出卡片有价值。

**验收**

- 23 个场次中，有歌单的 4 场能正确渲染场次页；其余场次页显示「歌单待补充（可提交更正）」；
- 同一个巡演（如 `Ave Mujica LIVE TOUR 2026「Exitus」`）的歌单对比页能算出「场场都唱」与「只唱过一次」两类曲目；
- 从歌曲页能反查到它出现的场次，点进去回到场次页（闭环）。

**工作量**：后端 3~4 人日（表 + 3 接口 + 对比聚合），前端 3~4 人日（3 个页面 + 矩阵组件）。数据回填 1 人日。

### 4.3 数据补全（和代码同等重要）

当前 **19 个场次没有歌单**。M1 的价值取决于这个数字。补全规则：

1. 只补有官方/可信来源的场次（官方 setlist 公告、官方 SNS、可靠的现场记录）；
2. 每条 setlist 提交时**必须挂 `source`**（第 3 节的表就是为这里准备的）；
3. 无法确认的场次，页面显示「暂无可靠歌单来源」，**不猜**。

## 5. 个人粉丝空间（M2）

目标：把公共资料变成"我的体验"，且**公开/私密明确分层**。

### 5.1 表设计

```sql
-- 关注扩展：target_type 增加 MEMBER / BAND / TOUR（复用 favorite，改注释即可，无需新表）

CREATE TABLE `user_song_state` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL, `song_id` BIGINT UNSIGNED NOT NULL,
  `state` VARCHAR(20) NOT NULL COMMENT 'WANT_TO_HEAR/LISTENED',
  `is_private` TINYINT NOT NULL DEFAULT 0,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`), UNIQUE KEY `uk_user_song` (`user_id`,`song_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='想听/已听';

CREATE TABLE `user_attendance` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL, `session_id` BIGINT UNSIGNED NOT NULL,
  `state` VARCHAR(20) NOT NULL DEFAULT 'ATTENDED' COMMENT 'WANT_TO_GO/ATTENDED',
  `is_private` TINYINT NOT NULL DEFAULT 0,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`), UNIQUE KEY `uk_user_session` (`user_id`,`session_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='想看/已参加';

CREATE TABLE `live_memory` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL, `session_id` BIGINT UNSIGNED NOT NULL,
  `rating` TINYINT NULL COMMENT '1~5',
  `content` VARCHAR(1000) NULL,
  `is_private` TINYINT NOT NULL DEFAULT 1 COMMENT '默认私密',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`), KEY `idx_session` (`session_id`), KEY `idx_user` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='个人现场回忆';
```

**分层原则**（直接写进接口）：`live_memory` 与 `user_song_state` 默认私有；任何"公开"内容一律走 `comment`（已有）或未来的 `contribution`，**永不让私人记录进入公共事实流**。

### 5.2 日历订阅（低成本高感知）

```
GET /api/v1/me/calendar.ics?token=<user_calendar_token>
```

- 为每个用户生成一个不可猜测的 `calendar_token`（存在 `user` 表新列），支持 iOS/Google 日历订阅；
- 事件 = 用户收藏的演出 + `event_reminder` 订阅的演出 + `user_attendance` 标记的场次；
- 输出标准 iCalendar（`BEGIN:VCALENDAR`，`DTSTART` 用 `live_session.start_time`，`SUMMARY` 用演出名，`LOCATION` 用场馆）；
- 同时提供一次性导出 `.ics` 下载（不暴露 token）。

> 这条能复用现有 `event_reminder`，是"提醒 → 日历"的自然延伸，工作量约 1 人日。

### 5.3 年度回顾

```
GET /api/v1/me/yearly/{year}
→ { listenedTop: [...], attendedCount, favoriteDelta: {...}, topBands: [...], setlistCoverage }
```

前端做成 `/me/yearly/:year` 的单页报告（不追求炫技，数据准确 + 好看即可）。**依赖 M1 的场次与 M2 的标记数据，排在 M2 末尾**。

**验收**

- 用户能把一场演出标记为"已参加"、写一句回忆、设为私密，其他人访问其主页看不到；
- 日历订阅链接能在手机系统日历里成功拉到场次；
- 年度回顾的数据与个人页统计一致（同一套聚合查询）。

## 6. AI 助手升级（M3）

目标：从"能查资料"变成"**有依据的资料向导**"。

### 6.1 回答附引用（依赖第 3 节）

Assistant v2 的事件流已支持 `status / delta / tool / confirm / done / error`。新增一种事件：

```json
{"type":"citation","items":[{"label":"官方 discography","url":"https://...","field":"release_date","verifiedAt":"2026-10-19"}]}
```

- 后端：`search_songs` / `get_song` / `get_event` 三个只读工具在返回结果时，连带 `fact_ref` 里的来源一起塞进工具上下文，最终由编排层输出 `citation` 事件；
- 前端：`MessageBubble` 在气泡下方渲染「依据」小卡片（可点击），**不做链接的富文本拼装**；
- Prompt 约束：材料里没有对应来源时，必须回答"站内暂无可靠来源"，禁止补全。

### 6.2 新的只读工具（组合查询）

| 工具 | 作用 | 复用 |
|---|---|---|
| `compare_setlists` | 两场/多场共有的曲目与差异 | M1 的 `setlist-compare` 聚合 |
| `band_timeline` | 某乐队按时间排列的演出 | `tour` + `live_session` |
| `song_live_appearances` | 某曲在哪些场次唱过 | M1 的 `/songs/{id}/live-appearances` |
| `data_health` | 缺来源、重名、字段冲突清单 | 只读聚合 SQL |

**关键设计**：Agent 工具**只调 Service，不写新 SQL**。上面四个新工具全部复用 M1 的查询能力，避免"AI 一套、页面一套"两份逻辑。

### 6.3 管理写操作：diff + 影响范围 + 撤销

现有确认卡片只有"工具名 + 参数"。升级为：

```json
{
  "type": "confirm",
  "token": "...",
  "title": "《迷星叫》的 MV 地址",
  "diff": [{"field":"mvUrl","from":"https://...old","to":"https://...new"}],
  "impact": {"affectedRows":1, "reversible":true, "undoWindowSec":86400},
  "preview": "..."
}
```

- `impact` 由工具实现方计算（例如"删除场次会级联删除 3 个票档、1 份歌单"）；
- `reversible` 为真的操作，`content_revision` 里保留 `before` 快照，支持 `POST /admin/revisions/{id}/revert`；
- 审计已有 `agent_tool_calls`（73 条），M3 把它与 `content_revision` 打通：一次 Agent 写操作 = 1 条 `agent_tool_calls` + N 条 `content_revision`。

**验收**

- 问「MyGO 9th 和 Ave Mujica Virtus 都唱了哪些歌」，回答带出共有曲目且每条结论有来源链接；
- 问一个站内没有依据的问题，回答明确说明缺少来源，**不编造**；
- 管理端让 Agent 改一条数据，卡片显示 `旧值 → 新值`，确认后能在 24 小时内一键撤销。

## 7. 搜索与发现（M4）

### 7.1 搜索（别名表的直接下游）

改造 `SearchService`，检索范围从「`song.title` + `band.name`」扩展到：

| 实体 | 匹配字段 |
|---|---|
| 歌曲 | `song.title` + `entity_alias.value`（ja/zh/romaji/abbr） |
| 成员 | `name_ja` + `name_romaji` + 别名 |
| 演出 | `live_event.title` + 别名 |
| 场馆 | `venue.name_ja` / `name_zh` |

实现建议（300~500 条数据量级，不要上 ES）：

```sql
SELECT ... FROM song s
WHERE s.is_deleted = 0
  AND (s.title LIKE CONCAT('%', :kw, '%')
       OR EXISTS (SELECT 1 FROM entity_alias a
                  WHERE a.entity_type='SONG' AND a.entity_id=s.id
                    AND a.normalized LIKE CONCAT('%', :kwNorm, '%')))
```

查询前把用户输入 `normalize()`（与写入时同一函数，保证对得上）。

### 7.2 可解释推荐

在歌曲详情页底部增加「相关」区块，规则**从强到弱、逐条可解释**：

| 规则 | 说明文案 |
|---|---|
| 同专辑其他曲目 | 「同一张专辑《…》」 |
| 同场次出现过 | 「在 2026-08-09 Virtus 同场演出」 |
| 同乐队 + 相近发行年份 | 「同乐队 2023 年发行」 |
| 标签重合 ≥2 | 「同标签：燃 / 夜勤」 |

后端一个 `GET /songs/{id}/related?limit=8`，按上述优先级合并去重。**每条都带 `reason` 字段**，前端直接显示理由——这正是"可解释"的落地方式。

**验收**

- 搜「みそしる」或「Misoshiru」都能命中「迷星叫」；
- 相关推荐的每一条都能说出理由，且理由可点到对应演出/专辑页。

## 8. 社区贡献与审核（M5）

```sql
CREATE TABLE `contribution` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL,
  `entity_type` VARCHAR(20) NOT NULL,
  `entity_id` BIGINT UNSIGNED NULL COMMENT '新增类提案可为空',
  `field` VARCHAR(40) NULL,
  `proposed_value` TEXT NULL,
  `evidence_url` VARCHAR(500) NULL COMMENT '必填（前端强校验）',
  `status` VARCHAR(20) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/ACCEPTED/REJECTED',
  `reviewer_id` BIGINT UNSIGNED NULL,
  `review_reason` VARCHAR(300) NULL,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_status_created` (`status`,`created_at`),
  KEY `idx_entity` (`entity_type`,`entity_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='资料更正提案';
```

- **前端入口**：歌曲/场次页每个可核验字段旁一个「提出更正」小链接（登录后可见）；
- **管理端**：`/admin` 当前 5 个标签，新增第 6 个「贡献审核」，左侧提案列表、右侧 diff 对照（复用 M3 的 diff 组件）+ 证据链接（新窗口打开）；
- **采纳动作**：把提案值写入正式表 → 自动生成 `content_revision`（`actor_type=ADMIN`，`source_id` 指向提案里的证据）→ `fact_ref` 状态更新为 `VERIFIED`；
- **不做**：不做用户直接编辑正式资料，不做积分体系。

**验收**

- 提案必须有证据链接才能提交（后端也校验，不只前端）；
- 采纳后，公开页面立刻显示新值，且「资料来源」里能看到这条证据；
- 拒绝要填理由，提案人能在个人中心看到状态与理由。

## 9. 音乐模型细化（M6，需触发条件才做）

这是本文档里**唯一建议"先不做"**的一项。

现状 `song` 表把"作品"和"专辑收录"揉在一起（`album_id` + `track_no` 单值）。要表达「原版 / 现场版 / 伴奏版 / 多专辑收录」需要拆成四层：

```
song_work（作品：一首歌的本质）
  └─ recording（录音版本：STUDIO / LIVE / INSTRUMENTAL / TV_SIZE）
       └─ album_track（专辑收录关系：album_id + track_no + 版本）
            └─ setlist_item 关联 recording（或 work）
```

**代价**：55 条现有数据要迁移，`album_id` 字段要废弃，前端 6 处引用要改，AI 工具 3 个要改。

**触发条件（满足任一再做）**：

1. 出现「同一首歌在多张专辑收录」的真实数据 ≥ 10 组；
2. 需要区分「TV-size / 完整版 / 现场版」用于时长与 MV 展示；
3. 歌单需要标明"这场唱的是哪个版本"。

在触发前，用 `song.stream_url` / `mv_url` 的差异 + `setlist_item` 已能覆盖 90% 的展示需求。**提前拆表只会增加成本，不会体现在页面上。**

## 11. 首条用户旅程的落地拆解

> 旅程：**发现一场演出 → 看每场歌单变化 → 点进某首歌追溯专辑与其他现场 → 把演出加入日历/写下回忆**

## 12. 工程约定与风险

### 12.1 沿用现有约定（不要另起一套）

- Migration 版本号从 **V54** 起（当前最高 `V53__order_concurrency_hardening.sql`）；
- 接口统一 `{code, message, data}`，前缀 `/api/v1/`；
- 新表一律带 `id / created_at / updated_at / is_deleted`（除纯关联表）；
- 管理端写操作必须写 `content_revision`；
- 前端字号不要用 `text-base`（项目 `--color-base` token 会让它变成颜色，用 `text-[15px]` 这类显式值）；
- 测试基线：后端接口测试 + 前端 Vitest（当前 82 例）+ Playwright E2E（当前 8 个 spec / 18 条用例），新功能同步补用例。

### 12.2 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **来源数据补不全** | "附依据"大面积空转，反而暴露数据薄弱 | M1 先做来源基座，**边做功能边补来源**；页面对无来源字段显式标注「待核验」而不是隐藏 |
| **歌单覆盖率低（4/23）** | 巡演对比页没有对比对象 | 优先补"同一巡演内"的场次歌单，先把对比做出来 |
| **事实错误** | 粉丝向事实出错会被立刻指出（本项目已发生 2 次） | 别名/成员/曲目数据一律先查官方源再入库，写入带 `source_id` |
| **AI 幻觉** | 回答"看起来对但没依据" | 无来源时必须说"暂无依据"；`citation` 事件为强制字段 |
| **范围失控** | 六个月做不完，功能都半成品 | 严格遵守第 2 节"三个不做"，M6 用触发条件卡住 |
| **双会话并行改同一文件** | 补丁重复执行、代码块重复（已发生多次） | 一个文件一个提交，提交前 `grep` 终态 + 构建 + 真机验证 |
