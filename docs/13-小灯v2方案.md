## 一、用户反馈与判断

| 反馈 | 本质 | 结论 |
|---|---|---|
| 「模式开关多余」 | 让用户理解系统内部结构，不是"真助手"该有的交互 | **删掉开关**，一个输入框，自动判定 |
| 「对话质量差」 | 回答像接口套壳：呆板、爱反问、乱猜 id、危险指令不设防 | 需要动提示词结构 + 循环校验 + 上下文 |

**一句话目标**：你对小灯说人话，它自己判断「这是聊天」还是「要动手」；动手时你看得见它在干什么，危险操作它先问你。

## 二、目标体验（三个场景，作为验收基准）

### 场景 A｜管理员随口问（不需要工具）
```
你：春日影是哪张专辑的？
小灯：（1~2 秒开始出字）《春日影》收录在 MyGO!!!!! 首张专辑《迷跡波》里，
      是剧场版…（流式输出，不调用任何工具）
```

### 场景 B｜管理员下指令（需要工具）
```
你：把迷星叫的 MV 换成 https://www.bilibili.com/video/BV1xx
小灯：🔧 正在查找《迷星叫》…
      🔧 找到 1 首（id=1，MyGO!!!!!）
      现在准备把《迷星叫》的 MV 从 BV1Ue4y117Xz 换成 BV1xx，
      确认吗？                        ← 内联确认卡片（显示人类可读标题，不是裸 id）
      [取消] [确认执行]
你：确认
小灯：✅ 已更新《迷星叫》的 MV 地址。
```

### 场景 C｜危险/含糊指令（要会拒绝、会追问）
```
你：把所有的演出都删了
小灯：批量删除我做不了，需要一场一场确认。最近有 2 场：
      ①《Ave Mujica 7th LIVE「Virtus」》②《MyGO!!!!! 9th LIVE…》
      你要删哪一场？                    ← 追问，不执行、不猜
```

> 三个场景的差别全部由后端判定，前端只有一个输入框。

## 三、架构改动（核心）

### 3.1 单一入口，删掉模式开关

| | 现在（v1） | v2 |
|---|---|---|
| 端点 | 问答 → `/assistant/chat/stream`（SSE）<br>运营 → `/admin/agent/chat`（非流式） | **统一** `POST /api/v1/assistant/chat/v2`（SSE） |
| 前端判断 | `isAdmin && opsMode` 选端点 | **零判断**，只连一个流 |
| 后端判定 | 无（两个服务各自为政） | 身份闸门 + 工具可用性 + 早退优化（见 3.3） |

`/assistant/chat`(v1) 与 `/admin/agent/chat` **保留不动**（已有测试依赖，且是回退路径）。

### 3.2 真流式（这是"像真助手"的关键）

**现状问题**：后端是「先拿到完整回复，再切片推送」——首字延迟 = 全生成时间（20~60s）。所以再好的文案都像卡住。

**v2**：直连 Ollama `stream: true`，边收边转发。

事件协议（SSE，`data:` 为 JSON）：

| event | 载荷 | 前端表现 |
|---|---|---|
| `meta` | `{conversationId, persona, canUseTools}` | 初始化（可选） |
| `status` | `{phase:'thinking'}` | 三点动画 |
| `delta` | `{text:'…'}` | 追加到气泡（真打字机） |
| `tool` | `{name, status:'RUNNING'\|'OK'\|'FAIL', summary}` | 灰色条目：`🔧 正在查找…` / `🔧 找到 1 首` |
| `confirm` | `{token, toolName, title, arguments, preview}` | 内联确认卡片（**含人类可读标题**） |
| `done` | `{intent, usedTools, elapsedMs}` | 结束（可显示耗时） |
| `error` | `{code, message}` | 提示（50301/40902 语义不变） |

**循环如何在流里跑**：一问一答可能包含「模型 → 工具 → 模型 → 文本」多段。策略：
- 每轮模型输出若产生 `tool_calls`，立即推 `tool(RUNNING)`，执行后推 `tool(OK/FAIL)`，再把结果回填发起下一轮
- 一旦出现 WRITE 工具 → 推 `confirm` 并**结束本轮流**（等用户点确认，确认接口单独调用，见 3.4）
- 文本 `delta` 只在"模型决定直接回答"或"工具跑完后的总结"阶段出现

### 3.3 路由判定（前端零逻辑，后端三级）

```
请求进来
 ├─ 1) 身份闸门：非 ADMIN → 工具集只给「只读 4 个」；ADMIN → 给全 8 个
 ├─ 2) 早退优化：消息 ≤ 12 字且不含动作动词（删/改/换/下架/恢复/创建/加/移除…）
 │        → 不挂工具，直接走问答（首字最快）      ← 避免闲聊也要等工具决策
 └─ 3) 其余 → 挂工具循环（模型自主决定用不用）
```

动作动词表放后端常量，**不是关键词精确匹配**,只是"是否可能涉及操作"的粗筛；筛错也无害（多挂工具而已，模型仍可不调用）。

### 3.4 确认流程（不变的部分）
- `confirm` 事件把 token 交给前端 → 用户点确认 → `POST /api/v1/admin/agent/confirm`（复用现有实现，含 token 一次性/本人/10 分钟过期）
- 确认结果作为一条新消息回到消息流（可以再走一次 `/chat/v2` 让模型复述，或直接本地渲染"✅ 已执行"——**v2 选择直接本地渲染**，省一次 20s）

## 四、对话质量：病灶与处方

| # | 现状病灶 | 证据 | 处方 |
|---|---|---|---|
| 1 | 人格压缩表达：`回答150字以内` + 睦只有 8 个字 → 运营场景说不出所以然 | 提示词第 6 条 + 人格卡 | 工具可用时切换为「运营提示词」：保留语气，但**放开字数**、允许结构化输出（列表/步骤） |
| 2 | 空话收尾：每条都以"是否需要…？"结尾 | 实测多次出现 | 提示词明确：**信息已足够时禁止反问**；只有真正缺参数时才问 |
| 3 | 乱猜 id：不问就填 `songId=1` | 有风险（写操作靠确认兜底，但体验差） | 确认卡片必须带**人类可读标题**：后端在生成 confirm 时用只读工具补查一次对象名（`《迷星叫》` 而非 `id=1`） |
| 4 | 同一错误反复重试 | 8B 模型常见 | 循环层加**同工具连续失败 2 次即停止**，把错误原样告诉用户并给下一步建议 |
| 5 | 批量危险指令可能连环执行 | 现在靠"一次一个确认"兜底 | 提示词 + 循环层双保险：单条指令内 WRITE 工具**最多产生 1 个待确认**，出现第二个直接终止并要求用户分次操作 |
| 6 | 记忆太短：8 条两轮就满 | `HISTORY_LIMIT=8` | 提到 16 条；更早的压缩为一行摘要（`[更早] 用户让改过 2 次 MV`），避免上下文过长拖慢 |
| 7 | 回答不知道"我是谁/能干什么" | 无能力自述 | 系统提示里加入「你能做的事」清单（读 4 项 + 写 4 项），问"你能干什么"要能准确回答 |
| 8 | 失败原因含糊 | `result` 直接透传技术错误 | 分类映射：40903→「该演出还有未完成订单，不能删」；参数错→「我理解错了参数，再试一次」 |

## 五、实施步骤（明天动手）

| 阶段 | 内容 | 产出 | 验收 |
|---|---|---|---|
| **M1** | 后端新增 `/assistant/chat/v2`：真流式 + 事件协议 + 身份闸门 | `AssistantV2Controller` + `StreamChatService` | curl -N 能看到 `status→delta→done` 事件 |
| **M2** | 接入工具循环（复用 `AgentToolRegistry` / 门控 / 审计），实现 `tool` 与 `confirm` 事件 | 循环服务改造 | 场景 B 全流程通 |
| **M3** | 质量处方 1–8 落地（提示词重构 + 循环层校验 + 确认卡片补标题 + 记忆 16 条） | 提示词与循环调整 | 场景 A/B/C 全通，且 A 首字 <3s |
| **M4** | 前端删开关，接 v2 事件（文档 12 的界面规格继续沿用） | 前端改 + 提示词更新 | 真机三档宽度 + 无 LLM 降级 |

**性能目标**：闲聊首字 <3s；需要工具的指令首字（工具条目）<3s、整体 <40s（本机 8B CPU）。

## 六、明确不做

- 不做"自动判断是否危险"的复杂分类器（用动词粗筛 + 确认门控足够）
- 不做多智能体/规划器（单轮工具循环够用，别过度设计）
- 不保留 v1 的模式开关（要删干净，不留兼容分支）
- 不为运营场景增加新人格（小灯一个就够，人格是闲聊特性）

## 七、风险

| 风险 | 应对 |
|---|---|
| 真流式下 tool_calls 与文本混排，Ollama 流式协议细节需试错 | M1 先用 curl 打样，确认 chunk 里 `tool_calls` 出现位置再写解析 |
| 首字速度受 CPU 限制（8B + 4 核） | 目标 <3s 是"开始出字"，不是回完；prompt 精简 + `num_predict` 上限 |
| 去掉开关后管理员偶尔想"纯聊天" | 不需要：模型自己不会乱调工具；担心的话只在设置里留一个隐藏开关（默认关） |
| 上下文变长（16 条）拖慢 8B | 只带最近 6 条完整 + 更早摘要；实测调 |
